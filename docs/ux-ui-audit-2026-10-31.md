# Аудит UX и UI системы UIKit

Дата: 31 октября 2026 года. Проверяемая библиотека: Brand UI 1.0.5, исходный
коммит `a0846ff`. Предмет аудита — сайты, формы, личные кабинеты и обычные
административные интерфейсы на существующей HTML/PHP-поставке.

**Основная рекомендация: развивать согласованность и готовые сценарии.** Основа
для сайтов уже достаточно широкая: две темы, формы, overlays, данные, состояния,
галерея и блоки страниц. Для универсального продуктового интерфейса прежде всего
нужны общая плотность, согласованные размеры, адаптация к контейнеру, оболочка
приложения и шаблоны работы с записями. Добавление десятков специальных виджетов
раньше этих задач увеличит стоимость поддержки быстрее, чем полезность набора.

Аудит фиксирует существующее поведение и проектирует следующую систему. Предлагаемые
размеры, API и компоненты ниже ещё не реализованы. Фирменный акцент, шрифты,
framework-free подключение, Bootstrap, Lucide и автономные примеры сохраняются.

## Состояние системы

| Область применения | Оценка готовности | Главная следующая задача |
|---|---|---|
| Лендинги и сайты услуг | Основное покрытие есть | Сдержаннее применять декор, проверить длинный реальный контент |
| Контентные сайты и каталоги | База есть | Компактные карточки, поиск и фильтры как законченная композиция |
| Формы заявок и пошаговые формы | Основные механизмы есть | Размеры полей, группы выбора, сводка ошибок, длинная форма |
| Личный кабинет | Частичное покрытие | Оболочка приложения, настройки, просмотр и редактирование записи |
| Плотная CRM или админка | Существенные пробелы | Плотность, toolbar, таблица, фильтры и панель деталей |
| Мобильный веб | Есть перестроение по ширине | Сценарии для касания, панели фильтров, клавиатура и реальные устройства |
| Аналитика, редактор, файловый менеджер | Требуют отдельных модулей | Добавлять по требованиям продукта |

В реестре каталога **43 копируемых примера и 19 разделов**. Это количество
демонстрационных документов, а не независимых компонентов: один пример объединяет
несколько компонентов, а часть примеров повторяет семью в составе страницы.

Сильные стороны, которые стоит сохранить:

- Семантические токены и вложенные light/dark темы уже отделены от сырых цветов.
- Формы сохраняют нативные значения и FormData; есть invalid/loading/success/error,
  отмена асинхронной работы и защита от повторного действия.
- Scoped init/destroy, очистка подписок и порталов позволяют встраивать компоненты
  в HTML/PHP и страницы с частичным обновлением.
- Есть empty/no-results/error/retry, skeleton, очередь toast, массовые действия
  таблицы, клавиатура overlays и возврат фокуса.
- Локальные шрифты, изображения, vendored-зависимости, полный HTML примеров,
  воспроизводимые ZIP и сохранённые проверки уже решают существенную часть интеграции.

## Сопоставление с готовыми системами

Сравнение основано на официальной документации, доступной на дату аудита. Эти
системы используются как источники решений о составе и поведении; перенос их
React-зависимостей в текущую поставку не требуется.

| Система | Что в ней реализовано и полезно здесь | Что перенять в UIKit |
|---|---|---|
| [Bootstrap 5.3](https://getbootstrap.com/docs/5.3/forms/form-control/#sizing) | Размеры полей `sm` и `lg`; уже является базой проекта | Сохранить ожидаемое действие классов размеров после применения темы |
| [Ant Design](https://ant.design/components/overview/) | Большой набор навигации, форм и отображения данных, включая Cascader, TreeSelect, Transfer, DatePicker | Использовать как контроль полноты продуктовых задач; специальные поля включать по реальному сценарию |
| [Carbon Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) | Несколько высот строк, согласованные toolbar и массовые действия, раскрытие строки | Проектировать плотность всей таблицы, включая её управление |
| [Mantine AppShell](https://mantine.dev/core/app-shell/) | Общая оболочка с header, navbar, aside, footer и отдельным состоянием мобильного меню | Дать переносимый каркас кабинета с согласованными областями прокрутки |
| [shadcn/ui](https://ui.shadcn.com/docs/components) | В каталоге есть Field, Item, Input Group, Button Group, Command, Sidebar, Sheet, Native Select и Empty | Отделить простые элементы, составные компоненты и композиции; дать понятный выбор между ними |
| [React Spectrum v3](https://react-spectrum.adobe.com/v3/theming.html#platform-scale) | Размер интерфейса учитывает точность указателя; темы поддерживают medium/large scale | Разделить плотность информации и размер области нажатия |
| [Ant Design Mobile](https://mobile.ant.design/zh/components/tab-bar/) и [ActionSheet](https://mobile.ant.design/zh/components/action-sheet/) | Отдельные TabBar и панель действий; у TabBar предусмотрен safeArea | Добавить мобильные композиции там, где меняется взаимодействие, сохраняя общие примитивы |

У Carbon актуальная шкала строк включает 24/32/40/48/64 px. Копировать всю шкалу
необязательно: для UIKit достаточно нескольких осмысленных режимов. Сам принцип
согласования строк и управляющих областей важнее количества размеров.
[Источник](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines).

Цвет также должен подчиняться иерархии: Spectrum описывает его как средство
выделения действий и смысла, с ограничением лишней цветовой нагрузки. Это
согласуется с существующим правилом умеренного лаймового акцента в DESIGN.md.
[Источник](https://spectrum.adobe.com/page/color/).

## Подтверждённые несогласованности

Приоритет P1 означает, что задача мешает использовать систему в нескольких
контекстах и должна предшествовать расширению набора. P2 улучшает частые сценарии.
P3 зависит от продукта. Это приоритет развития, а не классификация аварий.

| ID | Приоритет | Наблюдение | Следствие и решение |
|---|---|---|---|
| UX01 | P1 | `form-control-sm`, обычный input и `form-control-lg` измерены как 47 px; та же высота у трёх размеров select | Маленьких и больших полей фактически нет. Определить размерный контракт и синхронизировать нативные поля, trigger и составные controls |
| UX02 | P1 | `.btn-icon`, `.btn-sm.btn-icon`, `.btn-lg.btn-icon` все имеют 40×40 px | Icon button не подчиняется общей шкале. Задать размеры вместе с текстовой кнопкой и областью нажатия |
| UX03 | P1 | Обычная large-кнопка имеет 54,5 px при подписи «52 px». `brand-cta` даёт 41,5/49,5/57,5 px вместо указанных 36/44/52 | `min-height` задаёт минимум, padding и шрифт увеличивают итог. Исправить контракт, подписи и взаимодействие CTA с размерами |
| UX04 | P1 | Нет общего режима density для форм, списков, таблиц, меню и панелей | Смешивание `btn-sm` с полем 47 px и просторными строками не создаёт компактный интерфейс. Ввести наследуемую плотность |
| UX05 | P1 | Сетка шириной 320 px внутри viewport 1440 px сохраняет две колонки по 148 px | Карточки становятся узкими и чрезмерно высокими. Добавить адаптацию повторно используемых композиций к контейнеру |
| UX06 | P1 | Строки таблицы в демонстрации имеют 69 px с одной строкой текста; заголовок 60,5 px в каталоге и 68,5 px без него | Отступы, аватары и действия определяют плотность случайно. Согласовать строки, header, avatar, toolbar и pagination |
| UX07 | P1 | `catalog.css` меняет глобальные `.table th .btn`, checkbox и другие детали. В каталоге checkbox таблицы 16 px, автономно — 18 px | Один компонент демонстрируется по-разному. Ограничить стили оболочки и проверять одинаковую разметку с каталогом и без |
| UX08 | P2 | На 390 px таблица шириной 620 px находится в области примерно 293 px; альтернативного готового представления записей нет | Для чтения одной записи приходится двигать таблицу. Дать режим списка записей и переход к деталям; сравнение колонок оставить таблице |
| UX09 | P2 | В каталоге много текста 9–11 px; form label 12 px, поле 14 px; header таблицы 11 px | Большое количество визуально слабых подписей усложняет чтение. Упорядочить роли и увеличить значимый служебный текст |
| UX10 | P2 | Пример расширенных полей на мобильном начинает показывать сами поля примерно после 550 px высоты экрана | Навигация и повторяющиеся сведения о подключении занимают большую часть первого экрана. Свернуть технические сведения в каталоге |
| UX11 | P2 | В одном примере часто объединены разные сущности: avatar и chips; navbar, footer, drawer и popover; почти вся навигация | Состояния и размеры трудно проверять и находить по отдельности. Разделить карточки компонентов и сохранить большие примеры как композиции |
| UX12 | P2 | Responsive-проверки меняют viewport, но остаются desktop-эмуляцией; реальные touch, клавиатура телефона и screen reader не проверены | Геометрия уже подтверждена, качество мобильного взаимодействия ещё требует фактической проверки |
| UX13 | P1 | У формы консультации в каталоге промежутки между `.form-field` равны 20 px, а в копируемом полном HTML — 0 px | Внешний вид композиции зависит от `catalog.css`. Перенести необходимый ритм в переносимый компонент и проверить все копируемые композиции |

Доказательства: [измерения](audits/2026-10-31/evidence.json),
[поля и кнопки](audits/2026-10-31/size-probe-1440.png),
[узкая сетка в широком окне](audits/2026-10-31/container-probe-1440.png),
[мобильные формы и таблица](audits/2026-10-31/mobile-core.png).

Для UX01 причина видна в [ui-kit.css](../ui-kit.css): базовые `.form-control,
.form-select` переопределяют padding и font-size размерных классов Bootstrap.
Для UX03 `.brand-cta` отдельно задаёт 17 px, а `.btn` и размеры — padding и
min-height. UX05 следует из viewport media queries у `.brand-grid`.
UX06–UX07 воспроизводятся в [автономной таблице](../examples/table.html) и каталоге.
Для UX13 правило `.consultation-tool .form-field` находится только в `catalog.css`,
тогда как копируемый пример использует общую `.brand-surface` и те же `.form-field`.
Поведение формы сохраняется, визуальная композиция теряет межполевые интервалы.

## Состав компонентов и пробелы

«Есть» означает наличие стилей, поведения или документированного примера. Это
не заявление о ручной проверке всех сочетаний. «Частично» означает, что примитив
есть, но его варианты или законченный сценарий требуют доработки.

### Основы и действия

| Семейство | Сейчас | Нужное развитие |
|---|---|---|
| Цвет, темы, вложенные темы | Есть | Яснее разделить акцент действия, selection, focus и статус |
| Типографика | Есть H1–H6 и текстовые роли | Спокойные заголовки экранов приложения, числовые данные, моноширинный код |
| Отступы, контейнеры, сетки | Есть | Плотность, адаптация к контейнеру, правила вертикального ритма |
| Радиусы, тени, слои, motion | Есть | Матрица применения поверхностей и overlays; не добавлять новые шкалы без задачи |
| Button | Есть варианты, loading и disabled | Согласовать размеры, длинные подписи, расположение иконки и loading без скачка ширины |
| Icon button | Частично | Размеры, toggle/selected, цель касания, обязательное доступное имя |
| Button group и split button | Есть базовая возможность Bootstrap, отдельного полного примера нет | Оформить обычную группу и основное действие с меню дополнительных |
| Segmented control | Отдельного компонента нет | Выбор одного режима; различать radio, toggle и навигационные tabs |
| Ссылки | Есть базовый стиль | Текстовая, навигационная, внешняя, скачивание и ссылка с иконкой |
| Copy и keyboard hint | Копирование есть в каталоге | Небольшой переносимый компонент с результатом, ошибкой и доступной подписью |

### Ввод и формы

| Семейство | Сейчас | Нужное развитие |
|---|---|---|
| Input, textarea, helper, counter | Есть | Размеры, необязательность, описание формата, длинные label и error |
| Префикс, суффикс, clear | Есть | Одинаковая геометрия частей; иконка и ошибка не перекрывают значение |
| Password | Есть reveal и требования | Сценарий вставки и менеджера паролей, понятные тексты требований |
| Number | Есть step/min/max | Единицы, деньги и проценты как форматтеры; хранить исходное значение отдельно от показа |
| Checkbox, radio, switch | Есть; indeterminate используется в таблице | Группы с legend, описание и ошибка группы, строка целиком как label, карточки выбора |
| Range | Есть один thumb | Текущее значение и единица; два thumb — по сценарию диапазонного фильтра |
| Select | Есть собственное меню и native opt-out | Размеры и явный выбор native/custom; мобильный контракт |
| Searchable select, multiselect, autocomplete | Есть | Ограничение высоты выбранных chips, «ещё N», async-рецепт с отменой устаревших ответов |
| Date и time | Нативные поля есть | Общая композиция «с/по», пресеты и проверка диапазона; календарь опционален |
| File input и dropzone | Есть локальный выбор, ограничения и preview | Компактная строка прикрепления; загрузка/ошибка/отмена на уровне интеграционного рецепта |
| Form validation | Есть общий controller | Сводка ошибок со ссылками и серверные ошибки поля; момент показа ошибок описать отдельно |
| Stepper | Есть текущий шаг, проверка и итог | Компактное «Шаг 2 из 4», сохранённый черновик и возврат к изменению данных как рецепты |
| Search field | Базовые поля поиска есть | Самостоятельный пример: clear, pending, результаты, Escape, длинный запрос |
| OTP/PIN | Нет | Опционально для подтверждения входа; предпочтительно одно нативное поле с визуальным разделением |
| Color picker, rating, mentions, tree select | Нет отдельных компонентов | Только для конкретных продуктов, вне минимального ядра |

| Семейство | Сейчас | Нужное развитие |

| Tabs | Есть Bootstrap-пример | Много вкладок, длинные названия, мобильное переполнение и размерный контракт |
| Breadcrumbs | Есть | Длинный путь, текущая страница, компактный вариант с родительским переходом |
| Pagination | Есть | Короткий мобильный вид, диапазон записей и переход на первую/последнюю по необходимости |
| Dropdown | Есть | Группы, опасное действие, checkbox/radio-пункты только при соответствующей семантике |
| Accordion и disclosure | Есть Bootstrap accordion и нативный FAQ | Согласовать применение, вынести отдельный пример маленького disclosure |

### Блоки сайтов

Hero, преимущества, услуги, этапы, timeline, кейсы, отзывы, доверие, сравнение,
статистика, промо, FAQ, контакты и графика уже представлены. Основная потребность
здесь — правила композиции и контента: длина заголовка, количество CTA, варианты
без изображения, реальные длинные названия и пустые необязательные поля.
Бесконечное добавление визуально близких hero или карточек сейчас даст мало пользы.

## Предлагаемая модель всей системы

Система должна иметь четыре уровня: основы → компоненты → композиции → шаблоны
страниц. На каждом уровне сохраняется один источник решений. Каталог показывает
их отдельно, а полный пример объясняет совместное поведение.

| Уровень | Содержание | Критерий включения |
|---|---|---|
| Основы | Семантические tokens, typography, space, density, color, layers | Повторно используется несколькими семьями |
| Компоненты | Button, field, list item, badge, menu, dialog | Имеет понятную анатомию и самостоятельный контракт |
| Композиции | Toolbar, form section, filter panel, record list, detail panel | Решает повторяющуюся задачу из готовых компонентов |
| Шаблоны | Список с деталями, редактирование, настройки, вход, поиск, сайт | Показывает полный путь и состояния страницы |

Нужно различать три независимых измерения:

1. **Размер элемента** — small/default/large, когда требуется выделение или
   выравнивание соседних элементов.
2. **Плотность области** — compact/default, определяющая интервалы, строки,
   связанные controls, menu и skeleton согласованно.
3. **Взаимодействие и доступная ширина** — pointer/touch и широкий/узкий контейнер.
   Телефон уменьшает число колонок и количество видимых действий, но не требует
   уменьшать цели нажатия.

Отдельная копия каждого компонента с суффиксом mobile не нужна. Нужны правила
перестроения и несколько специализированных мобильных композиций. Вложенная
compact-панель должна оставаться независимой от default-страницы так же, как
сейчас независимы вложенные темы.

### Плотность и размеры

Ниже — стартовые значения для прототипа. Их следует проверить на длинном тексте,
двух темах, 200% текста и реальном касании до принятия в tokens.json.

| Роль | Default | Compact для точного указателя | Сенсорный сценарий |
|---|---|---|---|
| Основной control | Минимум 44 px, UI-текст 14 px | Минимум 36 px, текст 14 px | Цель минимум 44×44 px, редактируемый текст ориентировочно 16 px |
| Small / large control | 36 / 52 px | Явное локальное исключение, без дополнительного «сжатия» | Важные действия сохраняют удобную цель нажатия |
| Icon button | Согласовать с размером control | 36×36 px | Минимум 44×44 px для частых действий |
| Однострочная строка данных | Ориентир 48 px | Ориентир 40 px | Обычно 48–56 px и достаточная зона действия |
| Двухстрочная строка | По содержимому, ориентир от 64 px | По содержимому | По содержимому, перенос и доступные действия |
| Padding карточки/панели | 24 px | 16 px | 16 px в узком контейнере |
| Внутренний gap | 12–16 px | 8–12 px | Не уменьшать расстояние между целями ради компактности |
| Значимый вспомогательный текст | 12–14 px | 12–14 px | Обычно 14 px; основной текст 16 px |

Текущие токены 36/44/52 можно сохранить как основу. Field 46 px стоит либо
привести к общей шкале с учётом padding/border/line-height, либо явно объяснить
как отдельный размер. Переписывать его без проверки всех input group нельзя.
Высоты в таблице задаются как минимумы и могут расти от содержимого.

Плотность сокращает пустое пространство и вторичную информацию. Не следует
уменьшать весь интерфейс через `transform: scale()`, ставить текст 10–11 px или
скрывать обязательные labels. Размер цели и размер нарисованной иконки различаются.

44 px здесь — предлагаемая цель удобства и ориентир из WCAG AAA 2.5.5, а не
универсальная граница обязательного AA. WCAG 2.2 AA 2.5.8 использует 24×24 CSS px
с исключениями, в том числе по расстоянию между целями. Checkbox 16–18 px сам по
себе не доказывает нарушение: учитываются label, соседние цели и исключения.
[Минимальный target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html),
[расширенный target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html).

Предлагаемая настройка области: `data-ui-density="compact"`. Она должна менять
семантические CSS-переменные размеров и интервалов; имя API пока является эскизом.
Размерные классы Bootstrap следует поддержать явно, с документированным приоритетом
локального size над унаследованной плотностью. Внешний вид popup, перенесённого в
body, должен наследовать плотность исходного поля вместе с темой.

## Мобильные сценарии и узкие контейнеры

| Сценарий | Правило изменения | Условие готовности |
|---|---|---|
| Оболочка приложения | Постоянная sidebar становится drawer, вторичные действия уходят в меню | Сохранены текущий раздел, доступное имя, focus return и прокрутка рабочей области |
| Page header | Заголовок переносится; главное действие остаётся очевидным | Длинное имя и статус не вытесняют действие за экран |
| Toolbar и фильтры | Поиск остаётся рядом с результатами; сложные фильтры переходят в панель | Видно число применённых фильтров; Apply и Cancel имеют разный эффект |
| Таблица | При сравнении сохраняется scroll-область; первая значимая колонка может быть закреплена | Есть признак продолжения за краем; доступен контекст строки |
| Независимые записи | Список показывает 2–3 ключевых поля, статус и действие; остальные — в деталях | Выбор и данные сохраняются при смене представления |
| Pagination | Компактное «Назад · 2 из 12 · Далее» при большом количестве страниц | Кнопки удобны, диапазон результатов читается, смена страницы не теряет контекст |
| Form | Одна колонка; группы по смыслу; sticky submit только если не перекрывает содержимое | Клавиатура не закрывает поле/ошибку/действие; введённое не теряется |
| Select | Короткий простой выбор может быть native; длинный поиск — popup или полная панель | Клавиатура, список, выбранное значение и отмена работают на реальном телефоне |
| Multiselect | Несколько chips и «ещё N» вместо роста поля на полэкрана | Все выбранные значения доступны; удаление имеет понятную цель касания |
| Modal | Короткое подтверждение остаётся dialog; большая форма занимает удобную рабочую область | Header и footer не запирают содержимое, закрытие не теряет данные без предупреждения |
| Bottom panel | Для фильтров и короткого набора действий | Есть явное закрытие, Escape и доступная альтернатива жесту |
| Toast, cookie, закреплённые CTA | Общие правила размещения и safe-area | Элементы не перекрывают друг друга, фокус и обязательные действия |
| Cards и grids | Перестроение по ширине самого контейнера | Карточка в drawer читается так же, как в узкой колонке страницы |
| Tabs и breadcrumb | Контролируемое переполнение или сокращённый путь | Выбранный элемент виден, доступ к остальным не теряется |

Не нужно автоматически превращать любую таблицу в карточки: это разрушает
сравнение колонок. Представление выбирается по задаче. Если режим меняется,
предпочтительна одна активная семантическая структура или корректно скрытая
неактивная, единое состояние и уникальные ID.

Viewport и тип указателя не равнозначны: планшет с мышью и ноутбук с touch могут
иметь одинаковую ширину. Проверять нужно и узкий контейнер внутри большого окна,
и `pointer: coarse`, и экранную клавиатуру. Для нижних закреплённых элементов
нужны `safe-area-inset-*` и проверка динамической высоты окна. В текущем коде
`100dvh` уже используется для toast stack; общей safe-area-политики пока нет.

## Как сделать систему аккуратнее

### Типографика и иерархия

Сохранить Oswald в крупных заголовках сайтов и фирменных промо. Для заголовков
панелей, настроек, detail view и плотных рабочих экранов предпочесть существующий
Manrope, смешанный регистр и меньший перепад размеров. Это два контекста одной
системы, а не новая палитра или второй набор компонентов.

Ограничить повседневный выбор ролями display, page title, section title, body,
UI, helper, caption, number и code. Сырые размеры останутся внутри токенов;
`catalog-*`, micro, meta и note нужно пометить как внутренние либо постепенно
заменить семантическими alias без поломки старой разметки.

Числа, суммы и проценты выравнивать по задаче, применять tabular figures там, где
нужно сравнение разрядов. Не использовать uppercase для длинных фраз и мелких
labels. Не обозначать просто заполненное поле как успешное до фактической проверки.

### Поверхности и акцент

Одному смысловому блоку достаточно одной границы или спокойной поверхности.
Избегать последовательности «card внутри surface внутри card» с рамками и тенями
на каждом уровне. Тень использовать для подъёма, popup и overlay; обычную строку
данных отделять интервалом или тонким divider.

Лайм оставить главному действию, выбранному состоянию и редким смысловым акцентам.
Сайтный мазок и стрелку использовать в hero/CTA; таблицы, ошибки, настройки и
формы редактирования должны оставаться спокойными. Фирменная графика не требует
удаления: нужно ограничить область её применения.

Сейчас `brand-badge`, `brand-tag`, `brand-chip` уже решают разные задачи. Закрепить
термины: badge — статус или счётчик, tag — статичная категория, chip — выбираемый
или удаляемый фильтр. Размер и интерактивность не должны определяться случайным
выбором похожего класса.

### Ритм и содержание

Для рабочих экранов задать один шаг между полями и один между группами; helper
привязан к своему полю, error не создаёт визуально отдельную секцию. Иконки в строке
используются для узнавания типа, а не обязательного украшения каждого пункта.
Два рядом стоящих действия имеют понятную важность; редко используемые уходят в
overflow, опасные отделяются и называются конкретным глаголом.

Для каждого компонента нужен пример с коротким, типичным и длинным текстом,
отсутствующим изображением, большим числом элементов и пустым необязательным
полем. Демонстрационные одинаковые «Проект 1» не проверяют реальные ограничения.

## Полнота состояний

Каждому компоненту нужны только применимые состояния. Для статичного badge не
нужен loading; форма не должна получать readonly через несуществующий HTML-атрибут
select. Матрица помогает избежать случайных пропусков.

| Семейство | Обязательные состояния и переходы |
|---|---|
| Действие | Default, hover при подходящем указателе, focus-visible, pressed, disabled, loading, результат/ошибка действия |
| Поле | Пустое, заполненное, focus, invalid с причиной, disabled, readonly где применимо, autofill, reset, длинное значение |
| Выбор | Ничего/одно/много выбрано, disabled option, клавиатурный активный пункт, no-results, loading, error, отмена поиска |
| Коллекция | Initial loading, ready, empty, no-results, stale/refresh при необходимости, partial/error, retry с сохранением параметров |
| Изменение данных | Unsaved, saving, saved, validation error, network error, сохранение введённого, уход со страницы по правилам проекта |
| Overlay | Closed/opening/open/closing, Escape, outside click где допустим, focus trap/return, вложенный popup, длинное содержимое |
| Файл | Не выбран, выбран, неверный тип/размер, preview error; при сетевой интеграции — queued/uploading/done/error/cancelled |
| Доступ | Нет права на действие, нет доступа к разделу, истекла сессия, запись больше не существует |

Клавиатурные модели tabs, menu, combobox, dialog и toolbar различаются.
Использовать подходящий HTML и проверять по соответствующему паттерну
[WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/). Включать `role="menu"`
только ради внешнего вида нельзя: он меняет ожидаемое управление.

## Готовые композиции и страницы

После выравнивания основы нужны следующие переносимые HTML-примеры с callbacks
приложения и локальными данными:

| Шаблон | Состав | Состояния и мобильное поведение |
|---|---|---|
| Оболочка кабинета | Sidebar, header, breadcrumbs, page title, user menu | Текущий раздел, drawer, длинные имена, независимая прокрутка |
| Список записей | Search, filter bar, count, table/list, bulk, pagination | Empty/no-results/loading/error, выбор, компактный режим, фильтры в панели |
| Просмотр записи | Title/status/actions, description list, attachments, activity | Длинные значения, нет значения, нет доступа, удалена запись, детали на мобильном |
| Создание и редактирование | Form sections, выбор, файлы, action footer | Клиентские/серверные ошибки, saving, повтор, unsaved и сохранённые данные |
| Настройки и профиль | Группы настроек, avatar, password, switches | Изменено/сохранено/ошибка, зависимые поля, опасная зона |
| Вход и восстановление | Email/password, reveal, status, возврат к входу | Ошибка, loading, истёкшая ссылка; OTP только для выбранного способа входа |
| Поиск и каталог | Query, filters, sort, cards/list, count | Нет совпадений, сброс, длинный запрос, мобильная панель |
| Служебная страница | 403, 404, временная ошибка, offline | Понятный следующий шаг и возврат в контекст |
| Контент и сайт | Header, hero, reading, cards, FAQ, contact, footer | Длинный текст, anchor, несколько секций, компактная форма |

Не нужен обязательный backend: шаблон показывает состояния и события, а приложение
подключает сеть, авторизацию, серверную валидацию и реальные данные. «Готовый
UIKit» должен давать эти контракты, сохраняя возможность копировать обычный HTML.

## Что избыточно и что отложить

1. **Новые однотипные сайтные варианты.** Текущих 14 блоков достаточно для первого
   системного прохода. Полезнее законченная страница и правила выбора блока.
2. **Повторные системы стилей.** Дополнительные `.brand-gap-*` и собственный grid
   API поверх уже существующих Bootstrap utilities и tokens стоит вводить только
   для доказанного пробела. Сейчас это увеличит число равнозначных способов верстки.
3. **Дублирование поведения.** Новый confirm API может уменьшить boilerplate,
   но confirmation modal уже есть. Новое меню не должно создавать второй portal,
   focus trap и правила Escape рядом с действующими.
4. **Собственный календарь сразу.** Сначала пара нативных дат, ограничения,
   текст диапазона и пресеты. Calendar/date range с клавиатурой, locale и временем
   требует отдельного полноценного модуля, если нативного сценария недостаточно.
5. **Универсальный движок масок.** Денежный форматтер, дата, телефон и документы
   имеют разный контракт. Несколько явных форматтеров и сохранение исходного
   значения полезнее одной обязательной маски для всего.
6. **Большая таблица как spreadsheet.** Tree data, editing cell, drag columns,
   virtualization и server mode вводить по данным продукта. Сначала density,
   sticky/pin, visibility и понятное мобильное чтение.
7. **Редакторы, диаграммы, графы, map, kanban, file manager.** Сохранить как
   опциональные модули с собственными зависимостями и бюджетом поддержки.
8. **Builder страниц, новые framework-адаптеры, ESM/npm и Figma.** Это отдельные
   направления из этапа 11. Они не исправляют геометрию и сценарии текущего HTML UI.

Экспорт CSV **уже показан** в `examples/table.js` как bulk callback; встроенного
универсального exporter API нет. Сначала стоит документировать и при необходимости
обобщить этот рецепт. `confirm`, copy, localization и `.d.ts` полезны, но не должны
опережать размеры и рабочие страницы только потому, что их быстрее написать.

Не переносить все CSS в `@layer` одним механическим изменением: сейчас vendor
и проектные стили подключаются обычными файлами, и каскад имеет существующий
контракт. Сначала устранить глобальные стили каталога, проверить override-рецепты,
после этого отдельно проектировать миграцию слоёв.

## Каталог как инструмент выбора

Нынешние поиск, deep links, полный HTML, iframe с настоящим viewport и отображение
зависимостей стоит сохранить. Следующее развитие:

- Разделы «Основы», «Компоненты», «Композиции», «Страницы», «Подключение»; фирменные
  референсы и графику оставить в основах/блоках сайта.
- На странице компонента сначала назначение и живой пример, затем варианты,
  состояния и применение. Зависимости и длинный HTML раскрываются по запросу.
- Общие переключатели темы, density, ширины и состояния. Для responsive-проверки
  оставить iframe, а для контейнерной — реальную узкую область внутри широкого окна.
- Отдельная запись реестра для каждого компонента, общая композиция ссылается на
  эти записи. Установить независимые ID и информацию о статусе проверки.
- Матрица «состояние × тема × плотность × ширина» с явным «неприменимо»; строка
  `states` в метаданных сама по себе не означает, что состояние показано.
- Статус «проверено в Chrome» дополнить версией, датой и типом проверки, не
  распространять его автоматически на iOS, touch и screen reader.
- Инструкции выбора: select или autocomplete, chip или tag, toast или inline
  error, table или record list, dialog или drawer, tabs или segmented control.

## План реализации

План добавлен к [ROADMAP.md](../ROADMAP.md). В рамках текущего запроса выполняется
этап 13 с аудитом. Этапы 14–18 предложены и ещё не начаты. Каждый следующий этап
закрывается реализацией, документацией/интеграцией, проверками, актуальными ZIP
и отдельным локальным Git-коммитом.

Первый практический шаг — **DN01: зафиксировать размерный контракт**, затем
проверить один вертикальный срез: button + input + select + input group + одна
строка списка в default/compact, light/dark и узком контейнере. Только после этого
распространять решение на всю библиотеку. Новый бренд, стек и необязательные
специализированные модули для этого не нужны.

## Приёмка расширенной системы

Для значимых семейств проверять 320/390/768/1440 px, две темы, default/compact,
длинный контент, клавиатуру, отсутствие горизонтального scroll документа и работу
без каталога. Базовая матрица содержит **16 сочетаний** для 2 тем × 2 плотностей
× 4 ширин на выбранный сценарий. Она должна отражать реальные состояния и действия,
а не только количество PNG.

Дополнительно нужны контейнеры примерно 280/320/400/640 px в широком viewport,
coarse pointer, отсутствие hover, открытая клавиатура, длинные labels/chips,
сохранение выбора после фильтра/resize, errors из callback и поздние ответы.
Режимы reduced motion, forced colors, text spacing, 200% текста и reflow
добавляются к наиболее нагруженным композициям.

Проверить Chrome и Firefox, Safari/iOS с VoiceOver и Android Chrome на реальном
касании; для desktop screen reader выбрать доступную целевую среду, например
NVDA с поддерживаемым браузером. Эти среды нельзя объявлять проверенными по
Chrome CDP или по наличию ARIA-атрибутов. Если устройство недоступно, ограничение
остаётся явным условием поддержки, а не закрытым пунктом тестов.
